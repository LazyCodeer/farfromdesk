# Social actions: owner boundary assessment

Reviewed 30 October 2026 against the Local source and Apple's published documentation. This is an architectural assessment, not a proof that macOS cannot isolate processes. No real credential, account, signed installation, biometric prompt or running app was accessed or changed.

## What exists today

- The Local Node backend holds an admin bearer in the Local state folder ([config](../src/config.ts)). The existing Meta Brain key is a separate owner-readable file in that state folder ([Meta configuration](../src/meta-brain-config.ts)). Both use filesystem permissions, which do not separate other processes running as the same user. Some Local workers receive `WSB_STATE_DIR` ([masters](../src/masters.ts)). Their exact sandbox and OS permissions vary, so the risk depends on how a session is launched.
- Existing approvals mediate coding-tool requests and messages ([approvals](../src/approvals.ts), [masters](../src/masters.ts)). They do not give the social backend a separately authenticated proof that the owner reviewed an exact post. An admin bearer plus a `confirmed` field or backend-issued nonce can be replayed by a process that can read the bearer.
- The Flutter runner's current native channel manages login startup, not a protected social credential or approval broker ([MainFlutterWindow](../desktop/macos/Runner/MainFlutterWindow.swift)). The release entitlement disables App Sandbox ([entitlements](../desktop/macos/Runner/Release.entitlements)); the release signing script uses ad-hoc signatures ([signing script](../script/sign_macos_bundle.py)). An optional staged test signer requires an existing Apple identity but does not itself implement Keychain authorization or prove a social boundary ([test signer](../script/sign_local_test_app.py)). No real signing identities or Keychain items were inspected for this assessment.
- The existing desktop-control path can use Accessibility when granted, and its own documentation states it is not an OS sandbox against hostile same-user code ([desktop control](desktop-control.md)). A normal app confirmation button cannot establish a human action against a session that can automate that UI. The actual available automation permissions must be part of the threat model.

Accordingly, **live social research, generation, account setup and publication stay disabled**, including for the Local admin token. Local draft storage and deletion are not owner-isolated from a same-user process with access to the SQLite database or admin token. Deletion is logical, not secure erasure; WAL files, free pages, backups and snapshots can retain data.

## Reviewable alternative available now

The Local draft screen can copy the exact current caption for a manual handoff; it does not connect an account, send or publish. The owner can transfer it and any separately obtained image to an independently controlled device, inspect the actual account, caption and image in the platform's official interface, and choose whether to post there. The clipboard and local files can be read or changed by other processes with sufficient access on this Mac; verify the contents again on the receiving device. Moving content to another device is an owner action, not an automatic upload by Local.

## Candidate automated boundary, not implemented or verified

Apple's [TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains) distinguishes macOS's file-based and data-protection keychains. The latter uses code-signing-entitled access groups and optional `SecAccessControl`; Apple says those entitlements require an authorized provisioning profile and a user login context. Apple's [Keychain authentication guidance](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id) describes user-presence protection and notes that authentication contexts can permit reuse. This supports a possible design, but those APIs alone do not prove what content the owner saw or approved.

A candidate implementation would require all of the following, followed by an independent review:

1. A stable Apple-team-signed, provisioned and hardened native component with a narrowly scoped data-protection Keychain access group. Validate the installed signature, entitlements, update identity and OS behavior. Keep bearer tokens out of Node, loopback responses, worker-readable files and logs; do not reuse or silently migrate the existing plaintext Brain key.
2. An authenticated, narrowly scoped IPC boundary using the OS-supplied peer identity and verified signing requirement. A same-user worker, a forged executable, and a forged local HTTP request must not become a trusted caller. The trusted component must not blindly translate backend requests into approvals, expose credentials, or offer a headless publish command.
3. Review of the exact destination, caption and media in a surface the owner can trust, followed by fresh owner-presence authorization for each action. Bind one-shot authorization to an immutable content digest, destination and expiry inside the trusted component, then perform the provider call there. Test context reuse, accessibility automation, overlays, replay, changed drafts, concurrent attempts, cancellation, lock/unlock and failure. Biometric or passcode success proves user presence, not that the user actually reviewed particular content.
4. Durable, conservative handling of interrupted or ambiguous provider operations; no automatic retry that can duplicate a post. Separate explicit consent is needed for spending or uploading media. Meta's public-image URL and container ID do not themselves prove the bytes Meta fetched match the image reviewed. Do not enable Instagram publication until that exact-media problem has a verified solution or the owner explicitly chooses a manual platform review.
5. Synthetic adversarial tests on staged signed binaries: attempts by a same-user worker to read the key, impersonate a signer or call the broker, trigger the UI without owner presence, reuse an authorization, change content, and recover after a crash or uncertain provider outcome. Verify on the supported macOS versions and hardware. This task did not perform those tests or create a provisioning profile.

A signed broker is therefore a candidate, not a completed or verified solution. If the owner wants a guarantee against same-user UI automation, an independently controlled device or separately isolated execution environment is the concrete review path; the current app must not claim to enforce that guarantee.
